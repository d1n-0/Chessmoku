# Chessmoku (체스모쿠)

체스의 이동·포획과 오목의 연결 승리를 결합한 2인 웹게임. 흰 배경과 검정 테두리의 한국어 UI, 반응형 보드, 한 컴퓨터에서 번갈아 두는 오프라인 모드, 방 코드로 초대하는 온라인 친선전을 제공합니다.

## 실행

Node.js 22 이상:

```sh
npm ci
npm start
```

<http://localhost:3000>에 접속합니다. 개발 중 자동 재시작은 `npm run dev`입니다. 외부 CDN 없이 모든 게임 에셋을 제공합니다. 오프라인 모드는 한 컴퓨터의 브라우저에서 흑백을 모두 조작한다는 뜻이며, 최초 페이지 제공에는 로컬 서버가 필요합니다.

## Docker 배포 (HTTPS)

```sh
# 선택 사항: 설정 파일이 없으면 DOMAIN=localhost
cp .env.example .env

docker compose up -d --build --wait
```

기본 접속 주소는 <https://localhost>입니다. Caddy가 TLS를 처리하고, HTTP 요청을 HTTPS로 리다이렉트합니다. 온라인 친선전은 같은 주소의 `wss://` 연결을 사용합니다. 게임 서버의 3000 포트는 Docker 내부에서만 접근할 수 있습니다. 기본적으로 호스트의 TCP 80·443과 UDP 443 포트를 사용합니다. 이미 사용 중인 포트가 있다면 `.env`에서 `HTTP_PORT=8080`, `HTTPS_PORT=8443`처럼 바꿀 수 있으며, 이때 접속 주소는 `https://localhost:8443`입니다. 공개 도메인의 자동 인증서 검증은 외부 표준 포트 80/443이 필요하므로 비표준 포트는 로컬 시험용으로 사용하거나 별도 포트포워딩을 구성하세요.

### localhost 인증서

`localhost`에서는 Caddy가 자체 로컬 인증기관(CA)으로 인증서를 발급합니다. 컨테이너 안의 CA는 호스트 브라우저에서 자동으로 신뢰되지 않으므로 최초 실행 후 루트 인증서를 추출하세요.

```sh
docker compose cp proxy:/data/caddy/pki/authorities/local/root.crt ./chessmoku-local-ca.crt
```

추출한 **공개 인증서**를 접속할 운영체제/브라우저의 신뢰할 수 있는 루트 인증기관에 등록합니다. Windows에서는 인증서 가져오기에서 현재 사용자 → 신뢰할 수 있는 루트 인증 기관을 선택합니다. macOS에서는 키체인 접근으로 가져와 신뢰를 설정합니다. Ubuntu/Debian에서는 다음 명령을 사용할 수 있습니다.

```sh
sudo cp chessmoku-local-ca.crt /usr/local/share/ca-certificates/chessmoku-local-ca.crt
sudo update-ca-certificates
```

브라우저가 별도 인증서 저장소를 사용하는 경우 해당 브라우저에도 등록하고 다시 시작하세요. 다른 기기에서 사용할 때는 `localhost` 대신 실제 접근할 도메인을 설정해야 합니다. 이 인증서는 로컬 개발용이며 공개 도메인 배포에서는 수동 등록이 필요 없습니다.

### 공개 도메인 설정

`.env`의 `DOMAIN`을 자신의 도메인으로 변경합니다. `https://`나 경로 없이 호스트 이름만 입력하세요.

```dotenv
DOMAIN=play.example.com
```

도메인의 A/AAAA 레코드가 이 서버를 가리키도록 설정하고, 외부에서 서버의 TCP 80·443에 접근할 수 있도록 방화벽/포트포워딩을 구성한 다음 실행합니다.

```sh
docker compose up -d --build --wait
docker compose logs -f proxy
```

Caddy가 공개 인증서 발급·갱신을 자동 처리합니다. 공개 인증서의 실제 발급 성공 여부는 프록시 로그와 HTTPS 접속으로 확인하세요. `--wait`는 인증서 발급 완료까지 보장하지 않습니다. 구성은 [Caddy 자동 HTTPS 문서](https://caddyserver.com/docs/automatic-https)를 따릅니다.

### 운영과 데이터 보존

```sh
docker compose logs -f
docker compose down
```

`game-data`에는 기존 대국을, `caddy-data`에는 인증서와 CA를, `caddy-config`에는 프록시 설정 상태를 보존합니다. 기존 Compose 프로젝트명과 `game-data` 볼륨을 그대로 사용하므로 업데이트 시 저장된 방이 유지됩니다. `docker compose down -v`는 이 데이터를 모두 삭제합니다. 로컬 CA 볼륨을 삭제하면 새 CA 인증서를 다시 신뢰 등록해야 합니다.

HTTP 개발 서버가 필요하면 `npm start`로 <http://localhost:3000>에서 실행하세요. `PORT=8080 npm start`로 개발 서버 포트를 바꿀 수 있습니다. HTTP와 HTTPS는 브라우저 저장소가 별개이므로 기존 HTTP 주소의 오프라인 저장·재접속 정보가 HTTPS로 자동 이전되지는 않습니다. 서버에 저장된 방 데이터는 유지됩니다.

로컬 HTTPS 배포 검증은 루트 인증서를 추출한 뒤 실행할 수 있습니다. 인증서 검증을 끄지 않고 HTTPS 응답, HTTP 리다이렉트, WSS 방 생성·입장·행동 동기화를 검사합니다.

```sh
HTTPS_CA_FILE=./chessmoku-local-ca.crt npm run test:https
```

비표준 포트에서는 `HTTPS_URL=https://localhost:8443 HTTP_PORT=8080 HTTPS_CA_FILE=./chessmoku-local-ca.crt npm run test:https`로 검사합니다. 공개 도메인은 `HTTPS_URL=https://play.example.com npm run test:https`로 검사합니다.

서버는 단일 인스턴스로 운영합니다. 방 데이터는 JSON 원자적 파일 교체로 저장하며, 여러 프로세스가 같은 파일에 동시에 쓰는 구성은 지원하지 않습니다. 서버 재시작 시 클라이언트가 자동 재접속합니다. 양쪽이 오프라인인 방은 마지막 활동 후 24시간이 지나면 정리됩니다. 소규모 친선전용으로 최대 1,000개 방을 유지합니다.

## 화면 배치

데스크톱에서는 방 설정·보드·기보를 세 열로 나누고, 내 보관함을 보드 오른쪽, 상대 보관함을 왼쪽에 세로로 표시합니다. 모바일에서도 좌우 배치를 유지합니다. 보드 크기는 화면의 가용 너비와 높이에 맞춥니다. 전체 화면의 고정 최대 너비 제한을 없애 큰 화면에서도 공간을 활용합니다. 너비 1200px 미만에서는 상단 대국·기보 버튼으로 보조 패널을 열며, 대국 상태와 조작은 그대로 유지됩니다. 긴 기보와 대기열은 패널 안에서 스크롤됩니다. 아주 낮은 화면이나 확대 환경에서는 조작 가능한 최소 보드 크기를 유지하므로 페이지 스크롤이 생길 수 있습니다.

## 방 준비·권한·시간 설정

입장 순서대로 백·흑에 배정하며 두 플레이어가 준비해야 시작합니다. 준비 단계에서는 보드를 흐리게 처리하고 그 위에 시간 설정과 준비 버튼을 표시합니다. 모든 선수·대기자가 적용된 설정을 함께 볼 수 있으며 방장만 수정합니다. 대국 시작 시 설정창과 블러는 사라집니다. 준비 전에는 색상 변경도 가능합니다. 방장은 준비자가 없을 때 시간 설정과 대기자 선수 지정을 할 수 있습니다. 기존 선수는 대기열 마지막으로 이동합니다. 방장은 대국 중단(승패 없음)과 새 대국 준비를 할 수 있으며, 대기자가 되어도 권한을 유지합니다. 명시적으로 퇴장하면 남은 참가자 중 최초 입장자에게 방장 권한을 넘깁니다. 접속 끊김은 자동 권한 이전 사유가 아닙니다.

기본은 무제한입니다. 착수 제한 0~3,600초, 각자 총 시간 0~1,440분, 착수 후 추가 0~600초를 설정합니다. 0은 해당 제한 없음이며 추가 시간은 총 시간이 있을 때만 허용합니다. 두 제한을 설정하면 더 빠른 제한으로 시간패가 됩니다. 서버가 시계를 판정하고 브라우저는 남은 총 시간과 착수 시간을 표시합니다. 유효한 착수에만 추가 시간을 주며 연결 끊김·무르기 요청·서버 재시작 중에도 시간은 계속 갑니다. 무르기는 사용한 총 시간을 환불하지 않고 취소된 수의 추가 시간을 회수하며 착수 제한만 새로 시작합니다. 선수 교체·양보·재대국 후에는 준비를 다시 해야 합니다.

## 온라인 무르기

진행 중인 친선전에서 무르기를 누르면 상대에게 요청합니다. 상대가 수락하면 마지막 한 수(한 플레이어의 행동)를 되돌려 보드·보관 기물·차례·기보를 함께 복원합니다. 요청자는 취소, 상대는 거절할 수 있습니다. 요청 중에는 배치·이동을 잠시 중단합니다. 관전자와 종료된 대국은 요청할 수 없습니다. 연결 끊김·퇴장·자리 교체·서버 재시작 시 미처리 요청을 해제하고, 수락한 결과는 저장합니다. 서버에서 요청 ID와 대국 버전을 검증해 오래된 응답이나 요청자의 자체 수락을 차단합니다.

## 방 대기열과 보관 기물

이름(1~16자)은 입장 전과 방 안에서 설정할 수 있습니다. 대국자·대기자의 이름, 내 자리, 재접속 상태를 표시합니다. 접속 중인 대기자가 있으면 자리 양보로 현재 대국을 끝내고 대기열 마지막으로 이동할 수 있습니다. 색상 변경과 자리 양보 후에도 이름과 재접속 토큰은 본인에게 유지됩니다.

- 방은 플레이어 2명과 대기자 최대 16명을 수용합니다. 세 번째부터 입장 순서대로 대기하며 대국을 관전합니다. 대기 순번과 연결 상태를 표시합니다.
- 플레이어가 명시적으로 방을 나가면 진행 중인 대국은 기권 처리되고, 연결 중인 첫 대기자가 그 색의 자리를 이어받아 초기 상태의 새 대국 준비 단계로 돌아갑니다. 대기자가 없으면 이후 입장자가 빈자리를 채웁니다.
- 단순 연결 끊김은 자리를 비우지 않습니다. 대기자도 재접속 토큰과 순서를 저장하며 서버 재시작 후 복구합니다. 오프라인 대기자는 승계 시 건너뛰고, 재접속하면 남아 있는 순서로 돌아옵니다. 대기자가 방을 나가면 대기 등록과 토큰을 삭제합니다.
- 대기자는 배치·이동·기권·재대국을 요청할 수 없습니다. 다른 참가자의 재접속 토큰은 공개하지 않습니다.
- 양쪽 보관함의 기물별 수량이 배치·포획·무르기·재대국마다 갱신됩니다. 온라인에서는 내 보관함과 상대 보관함, 오프라인·관전에서는 현재 차례와 반대색 보관함을 표시합니다. 상대 보관함은 읽기 전용입니다.

## 게임 규칙

- **보드:** 8×8 보드에 백 킹 e1·흑 킹 e8 선배치, 백 선공. 각 턴에 배치 또는 이동 중 한 가지 행동.
- **초기 보관함:** 각자 폰 8, 룩 2, 비숍 2, 나이트 2, 퀸 1. 킹 1개는 이미 보드 위에 배치되어 총 16개 기물로 시작.
- **배치:** 보관함의 기물 하나를 빈 칸 어디든 배치. 배치로 포획 불가. 첫 수에도 기물 종류·진영 제한 없음.
- **이동:** 일반 체스의 기물별 이동. 나이트 외 기물은 다른 기물을 뛰어넘지 못함. 자기 기물 포획 불가.
- **포획:** 잡은 기물은 자신의 색으로 보관함에 추가. 이후 자신의 턴에 재배치 가능. 재배치한 폰의 이동 이력은 초기화.
- **폰:** 백은 8행 방향, 흑은 1행 방향으로 한 칸 전진, 대각선 앞의 적 포획. 백 2행 / 흑 7행에서 아직 이동하지 않은 폰은 경로가 비었을 때 두 칸 전진 가능. 다른 행에서는 첫 이동이어도 한 칸. 끝 행에 도달한 폰은 승격하지 않아 이동할 수 없음.
- **승리:** 종류와 관계없이 같은 색 기물을 가로·세로·대각선으로 **5개 이상** 연속 연결하거나, 상대 킹을 **실제로 포획**. 두 조건을 동시에 충족하면 킹 포획으로 표기.
- **체크:** 일반 체스의 체크 강제 대응이나 킹의 위험 칸 진입 제한은 없음. 이 게임의 체크메이트는 실제 킹 포획을 의미.
- **제외:** 프로모션, 캐슬링, 앙파상, 쌍삼 금지. 6목 이상도 승리.
- **무승부:** 다음 플레이어에게 배치·이동 가능한 행동이 없을 때. 반복수·50수 규정 없음. 온라인 시간제한은 방 설정에 따름.

원 요청에서 지정하지 않은 보드 크기, 장목, 폰의 첫 두 칸 이동 등은 위 규칙으로 구체화했습니다. 킹은 처음부터 보드 위에 있으며 5목을 구성하는 기물로도 계산합니다. 색 교환이나 추가 선공 보정은 적용하지 않습니다.

## 조작 및 모드

규칙·기물 이동·에셋 출처는 `/rules`에 분리했습니다. 상단 규칙 링크는 새 탭에서 열려 진행 중인 대국 연결을 유지합니다.

보관함 기물을 클릭한 뒤 빈 칸을 클릭하면 배치됩니다. 내 기물을 클릭하면 이동 가능 칸이 표시됩니다. 같은 기물을 다시 누르거나 Escape를 누르면 선택을 해제합니다. 보드는 Tab 및 방향키로 탐색하고 Enter/Space로 조작할 수 있습니다.

- **오프라인:** 흑백을 같은 화면에서 번갈아 조작. 새 대국, 한 수 무르기, 보드 뒤집기, 기권, JSON 기보 저장 지원. 브라우저 localStorage에 대국을 자동 저장하고 새로고침 시 복원. 킹 선배치 도입 전 저장된 대국은 기존 배치를 유지하며, 새 대국부터 새 시작 배치를 적용.
- **친선전:** 방 생성자는 기본 백, 입장자는 빈자리에 배정. 준비 전 흑·백 선택 가능하며 상대가 있으면 요청·수락으로 변경. 지정된 두 플레이어가 모두 준비하면 시작. 서버가 모든 행동을 검증하고 상태 버전으로 중복·오래된 수를 거절. 대기자는 색상 변경 불가. 요청 중에는 수를 둘 수 없으며 거절·취소·연결 끊김 시 요청 해제.
- **재접속:** 같은 탭 새로고침 시 sessionStorage의 비공개 재접속 토큰으로 복원. 상대가 일시적으로 연결을 잃으면 착수는 중단되지만 시간제 시계는 계속 진행. 탭을 닫아 토큰을 잃으면 해당 자리 복구 불가. 방 코드는 새 자리 입장용이며 이미 찬 방의 자리를 탈취할 수 없음.
- **종료:** 진행 중 명시적으로 방 나가기/기권은 패배. 연결 끊김 자체로 자동 패배하지 않음. 재대국은 양쪽 동의 후 준비 단계로 돌아가며 킹을 e1·e8에 다시 배치. 기존 온라인 방의 진행 중 대국은 유지. 결과 창을 닫은 경우 보드 아래 결과 · 재대국 버튼으로 다시 열림.

## 구조

```text
shared/
  game.js                 규칙 엔진 공개 API (기존 import 경로 유지)
  game/                   초기 상태, 이동, 승리 판정, 행동 적용, 저장 기보 재생
server/
  index.js                프로세스 시작·종료
  app.js                  HTTP·저장소·WebSocket 조립
  http.js                 페이지 라우팅·정적 파일·보안 헤더
  websocket.js            연결·재접속·브로드캐스트·heartbeat·요청 제한
  rooms/service.js        방 생성·입장·대기·대국·기권·재대국 처리
  rooms/players.js        이름 검증·색상 합의·자리 양보
  rooms/connections.js    참가자 연결·관전 방송·대기자 자리 승계
  rooms/repository.js     방 스냅샷 로드·원자적 파일 교체 저장
  pages/                  대국·규칙 HTML
public/
  js/main.js              브라우저 진입점
  js/game-controller.js   사용자 입력과 로컬/온라인 대국 흐름 조정
  js/connection.js        WebSocket 연결·전송·재연결
  js/storage.js           브라우저 저장소와 기존 저장 호환
  js/download.js          기보 파일 내보내기
  js/ui/                  보드·보관함·기보·대국 상태·대화상자 렌더링
  styles/                 공통·대국·규칙 페이지 스타일
  assets/                 기물·폰트 에셋
scripts/                  밸런스 실험 도구
test/                    규칙·HTTP·WebSocket·저장 복원·브라우저 테스트
```

의존성은 UI/서버에서 `shared` 규칙 엔진으로 향합니다. 규칙 엔진은 DOM·파일·네트워크에 의존하지 않습니다. UI 컴포넌트는 전달받은 상태를 표시하고, 상태 변경과 사용자 입력은 컨트롤러에서 처리합니다. 통신 모듈은 콜백으로 수신·연결 이벤트를 전달합니다. 서버는 저장소와 방 처리에 필요한 연결 작업을 생성 시 주입합니다.

페이지 URL은 `/`, `/rules`이며 HTML 파일명과 분리됩니다. 기존 `/rules.html`, `/index.html` 주소는 각각 정식 경로로 308 리다이렉트합니다. 저장 형식·방 프로토콜·기보 내보내기 형식은 유지합니다.

규칙 변경은 `shared/game/`, 화면 변경은 `public/js/ui/`와 `public/styles/`, 방 정책 변경은 `server/rooms/service.js`에서 시작하면 됩니다. `npm run format`으로 코드 포맷을 적용하고 `npm run format:check`로 검사합니다. 변경 후 `npm test`와 `npm run test:e2e`를 실행합니다.

`PORT`(기본 3000), `DATA_DIR`(기본 `./data`) 환경변수를 지원합니다. 방 코드에 재접속 토큰을 포함하지 않으며 서버는 상대 토큰을 전달하지 않습니다. 데이터 디렉터리는 정적 파일로 공개하지 않습니다. 에셋의 출처 및 라이선스는 [ATTRIBUTION.md](ATTRIBUTION.md)를 참조하세요.

## 밸런스 실험

실제 서비스의 규칙을 바꾸지 않고 `scripts/balance.mjs`에서 킹 선배치와 첫 수 제한 등의 변형을 비교합니다. 연결·균형·기물 확보 성향의 봇 3종을 흑백 모든 조합으로 대전시키며, 실제로 둔 모든 수는 프로덕션 규칙 엔진과 교차 검증합니다. 별도 실험에서만 4목을 판정합니다.

```sh
# 킹 선배치 기준안과 양쪽 첫 수 자기 진영 배치안을 새 시드로 비교
node scripts/balance.mjs --variants=kings5,bothHome5 --seeds=24 --seedStart=101 --depth=4 --width=8 --workers=14 --out=analysis/balance/holdout

# 전체 집계와 그림 생성 (그림만 matplotlib 필요)
PYTHONNOUSERSITE=1 python3 scripts/summarize-balance.py
```

- [전체 집계 CSV](analysis/balance/comparison.csv), [JSON 및 전략별 결과](analysis/balance/comparison.json), [탐색 깊이별 비교 그림](analysis/balance/comparison.svg).
- 각 단계의 `*.meta.json`에는 규칙·봇 평가 가중치·시드·탐색 설정을, `*.jsonl`에는 모든 대국의 결과와 전체 수순을 저장합니다. `p@52`는 폰을 보드 인덱스 52에 배치, `60>52`는 60에서 52로 이동입니다. 인덱스 0은 a8, 63은 h1입니다.
- 시드별 기물 배치를 좌우 반사해 좌표 선택 편향을 확인합니다. 흑 선공 대조군과 색을 반전한 초기 배치의 결과도 검증합니다. 반복 키에는 보드·차례·보관함·폰 이동 이력이 포함됩니다.
- 후보를 제한하는 탐색이므로 최적 플레이를 보장하지 않습니다. 1수 탐색도 상대의 즉승 수를 피합니다. 2수 탐색은 자신의 상위 후보와 상대의 모든 답수를 정적으로 비교하고, 3수 이상은 양쪽의 상위 후보를 재귀 탐색합니다. 모든 단계에서 즉승과 즉패 수를 검사하지만 조용한 전술은 놓칠 수 있습니다.
- 동일 상태 3회 또는 120회 행동에서 **실험만 중단**합니다. 미종료를 무승부나 반 승점으로 계산하지 않으며, 백 승률의 분모에는 승패가 난 대국만 포함합니다. 고정 백 첫 수 변형의 길이는 고정 배치 이후 행동 횟수입니다.
- 초기 1~24 시드 비교 후, 최종 두 후보는 사용하지 않은 101~124 시드와 더 넓은 후보 탐색으로 재검증했습니다. 신뢰구간은 시드 단위의 대응 부트스트랩이며, 해당 봇 안의 변동성을 나타낼 뿐 사람의 승률을 뜻하지 않습니다.

이번 실험은 총 6,480판이며, 색 반전 대조 648쌍의 결과 일치를 확인했습니다. 새 시드의 최종 4수·후보 8개 비교 결과:

| 규칙 | 백 승 | 흑 승 | 실험 중단 | 결정된 대국의 백 승률 |
| --- | ---: | ---: | ---: | ---: |
| 킹 선배치·5목 | 121 | 85 | 10 | 58.7% |
| 양쪽 첫 수 자기 진영 배치·5목 | 127 | 81 | 8 | 61.1% |

두 안의 백 승률 차이(제한안 - 기준안)는 +2.3%p였고, 대응 시드 부트스트랩 95% 구간은 -2.22~+6.47%p였습니다. 추가 제한의 개선 효과를 확인하지 못했습니다. 기준안에서는 승부가 난 206판 중 킹 포획 150판, 5목 56판, 종료 행동 수 중앙값 23수였습니다. 이번 봇 실험은 5목을 4목으로 줄여야 한다는 근거를 제공하지 않았습니다.

현재 권고는 **킹 선배치·5목 유지, 추가 첫 수 보정은 보류**입니다. 백 첫 수 폰 제한은 2수 탐색에서 백 승률 46.0%였지만 3수 63.7%, 4수 72.2%로 바뀌어 안정적인 보정으로 볼 수 없었습니다. 이러한 수치는 사람의 승률이나 필승 전략의 증명이 아닙니다. 실험 당시에는 서비스 규칙을 변경하지 않았으며, 이후 킹 선배치·5목 유지안을 서비스에 적용했습니다. [최종 비교 그림](analysis/balance/holdout.svg)과 [부트스트랩 구간](analysis/balance/holdout-intervals.json)을 함께 확인할 수 있습니다.

브랜드명은 **Chessmoku**, npm 패키지와 Docker 이미지 이름은 `chessmoku`입니다. 기존 대국과 재접속 호환성을 위해 브라우저 저장 키와 기보 형식 식별자 `five-crown-v1`은 유지합니다. Docker Compose 프로젝트명과 데이터 볼륨도 유지합니다.
